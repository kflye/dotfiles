# PR Review Response

Work through a review on a pull request **as the author**: read all of it,
apply the suggestions genuinely warranted, answer questions, resolve threads
once settled, and keep the PR's title, description, and history clean as the
change evolves.

A review comment is an input to your judgement, not an order to execute — you
own the correctness of the code you merge. Approving and merging stay the
reviewer's call; this skill stops at getting the branch review-ready.

## Process

### 1. Gather the full review

Load the complete state before changing anything — acting on a partial view is
the first mistake:

- The PR itself: title, description, current branch, CI status
  (`gh pr view <n>`, `gh pr checks <n>`).
- **Every** comment: top-level review summaries, inline code comments, general
  PR comments (`gh pr view <n> --comments`, and `gh api` for review threads).
- Check out the PR branch locally (`gh pr checkout <n>`), and commit only there.

### 2. Read each thread in full before acting

- Read the whole thread top to bottom. A later reply may refine, soften,
  retract, or reverse the original — the first message alone is not the point.
- Group related comments to grasp the reviewer's overall intent, not isolated
  lines.
- Sort each into **code suggestion**, **question**, or **observation** (no change
  needed).

### 3. Evaluate each code suggestion critically

Judge two things per suggestion, and apply only what survives both:

1. **Is it actually good?** — correct, consistent with the project's
   conventions, an improvement. A reviewer can be mistaken or lack context you
   hold. Where you believe a suggestion is wrong, reply with your reasoning and
   let the thread settle rather than applying it.
2. **Literal or a hint?** — many comments point at a problem without prescribing
   the fix ("this feels fragile", "could be extracted"). Address the real intent,
   which is often a better fix than the words.

For anything you change, re-run the project's build, format/lint, and tests —
the comment is addressed only once they pass.

### 4. Answer questions, and ask when unclear

- Answer every question in the thread where it was raised, referencing the
  commit or line that addresses it.
- When a comment's meaning is unclear, ask a follow-up in that thread and wait
  for the reply — an unanswered question is a blocker, and guessing then silently
  changing code to match is the failure to avoid.
- **Mark every comment you post as agent-generated.** You post under the user's
  identity, so a reader cannot otherwise tell your reply from theirs. Begin each
  one with an unambiguous marker (e.g. `🤖 _Generated by an agent on behalf of
  @<user>_`). This covers answers, follow-up questions, and replies alike.

### 5. Commit the changes

Make small, descriptive commits — one coherent change each, message saying what
changed and why. Push to the PR branch so they attach to the open review.

### 6. Keep the branch in sync by rebasing

- Update the branch only when the PR is actually behind its base. Bring it up to
  date by **rebasing** onto the base (`gh pr update-branch <n> --rebase`, or the
  "Update branch" button), keeping history linear.
- Merging the base into the feature branch is the thing to avoid — no
  `git merge main`, no "Update with merge commit".
- After a rebase, re-run build, format/lint, and tests: it may have picked up
  changes that affect your work.

### 7. Resolve settled threads

Mark a thread resolved (`gh api graphql`, `resolveReviewThread`) once it is
genuinely settled — the change made or the reviewer agreed none is needed, and
any question answered. A thread where you declined a suggestion stays open until
the reviewer agrees; a thread with an open follow-up stays open.

### 8. Keep the PR title and description honest

When addressing the review changes what the PR does — scope, approach, or
behaviour — update the description to match, and the title if it no longer
describes the change. Keep the summary, testing notes, and any linked references
consistent with the branch's final state.

### 9. Report

Summarize for the user:

- Each comment/thread and how it was handled — applied, declined (with reason),
  answered, or awaiting a reply.
- Threads left unresolved and what each waits on.
- Commits added, and whether the title/description changed.
- Whether the branch was rebased to stay in sync.
- Build, format/lint, and test status after the changes.

### 10. Harvest reusable knowledge

Load `skill-harvesting` and reflect on whether anything from the review — a
reviewer correction, a convention they insisted on, a recurring pushback —
should become a new skill or update an existing one. Only cross-project,
non-default insights qualify; finding nothing is a valid outcome. Present
candidates for approval before creating anything.
